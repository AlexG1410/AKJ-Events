## Project

AKJ Events is a single-module Android app (`:app`, package `co.edu.uniquindio.akjevents`) for discovering community events, built as a university class project. It is in "Fase 3" (final delivery), done step by step. Accounts already use Firebase: `FirebaseUserRepository` (Firebase Authentication plus the `users` and `pointsHistory` collections in Firestore, guides 19 and 20) handles register, login, logout, password reset by email and profiles. Firebase keeps the session; «Recordar este dispositivo» is stored with DataStore (`DataStoreSessionPreferences`, guide 13) and checked at startup by `RestoreSessionUseCase`. Events, comments, attendances, interests and notifications are in Firestore too (`FirestoreEventRepository`, `FirestoreNotificationRepository`; collections `events`, `comments`, `attendances`, `interests`, `notifications`), listened to in real time while a session is open. Capacity and counts change inside Firestore transactions; attendance and interest documents use the id `eventId_userId`. `firestore.rules` enforces permissions in the database (only moderators verify; organizers edit their own events but cannot verify them; nobody can give themselves the moderator role; each person reads only their notifications; pending and rejected events are readable only by their organizer and moderators, so the events query depends on the session's role). Points and badges are written by other users' actions, so any signed-in user may change only `points` and `badges` on a profile (a known limit: Cloud Functions would need the paid plan). Sample data is loaded with `seed/seed.mjs` (Firebase Admin SDK, skips if `events` already has data unless `--force`): sample organizer profiles without Auth accounts, the 15 sample events, comments, attendances and interests. Moderators are preloaded: create the account in Firebase Console → Authentication, sign in once (the app creates a `USER` profile) and change `role` to `MODERATOR` in Firestore. Code comments and the README are in Spanish; keep new comments in Spanish.

Firebase setup: `app/google-services.json` (project `akj---events`) and the `com.google.gms.google-services` plugin; `di/FirebaseModule` provides `FirebaseAuth` and `FirebaseFirestore`. For local testing use the Firebase Emulator Suite (`firebase.json`: Auth on 9099, Firestore on 8080). Start it with `firebase emulators:start --only auth,firestore` (on this machine set `JAVA_TOOL_OPTIONS=-Djdk.net.unixdomain.tmpdir=C:\Users\Public` first, same loopback issue as Gradle), run `adb reverse tcp:9099 tcp:9099` and `adb reverse tcp:8080 tcp:8080`, and build with `-PuseFirebaseEmulator=true -PfirebaseEmulatorHost=127.0.0.1` (in PowerShell, quote each `-P` argument). Plain `10.0.2.2` timed out from the app on this machine. The emulator loads `firestore.rules` (hot reload on save) and starts empty: run `cd seed && npm install && FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 node seed.mjs` after each start. For the real project, the seed needs `GOOGLE_APPLICATION_CREDENTIALS` pointing to a service-account key kept outside the repo (`.gitignore` blocks `*-firebase-adminsdk-*.json`), and the rules are published with `firebase deploy --only firestore:rules`. The debug build allows cleartext only to the emulator hosts (`src/debug/res/xml/network_security_config.xml`). Automated tests must sign in only against the emulator, never the real project.

Internationalization (guide 14): the app is in English and Spanish. Every user-facing text lives in `res/values/strings.xml` (English, the default) and `res/values-es/strings.xml` (Spanish), with the same keys and the same `%1$s`/`%1$d` arguments; `StringsTranslationTest` fails if one is missing. Never hardcode visible text: composables use `stringResource`/`pluralStringResource`; ViewModels get an injected `ResourceProvider` (`core/util`, bound in `di/AppModule`); messages a `UiState` computes by itself (field errors) are `UiText` and the screen calls `asString()`. Domain enums carry no text: their labels are the `labelRes`/`descriptionRes`/`reasonRes` extensions in `core/util/Labels.kt`, and UI enums (tabs, filters) hold a `@StringRes Int`. Stored data is language-neutral: `AppNotification` and `PointsEntry` save the type plus data (event title, actor, detail, badge, level) and the screen builds the sentence in the reader's language; text written by people (comments, rejection notes, notices) is shown as written. Dates use `EventFormat` (composable, device locale). `res/xml/locales_config.xml` enables the per-app language setting (Android 13+); from adb: `adb shell cmd locale set-app-locales co.edu.uniquindio.akjevents --locales es`. Unit tests pass `TestResourceProvider`, which reads the Spanish strings, so assertions keep checking Spanish messages.

Toolchain: JDK 17, Gradle 9.6, AGP 9.4, Kotlin 2.4, compileSdk/targetSdk 37, minSdk 28. Dependency versions live in `gradle/libs.versions.toml`.

## Commands

Use `./gradlew` (Git Bash) or `.\gradlew.bat` (PowerShell) from the repo root.

- Build debug APK: `./gradlew assembleDebug`
- Install on a running emulator/device: `./gradlew installDebug`
- Unit tests (JVM): `./gradlew testDebugUnitTest`
- Single unit test: `./gradlew testDebugUnitTest --tests "co.edu.uniquindio.akjevents.PublicEventVisibilityTest"` (append `.methodName` for one method)
- Instrumented tests (needs device/emulator): `./gradlew connectedDebugAndroidTest`
- Android lint: `./gradlew lint`

## Architecture

Single-Activity Jetpack Compose app (Material 3). `MainActivity` sets `AKJEventsTheme { AppNavigation() }`; everything else is composables.

Source is split by layer under `app/src/main/java/co/edu/uniquindio/akjevents/`:

- `core/` — cross-cutting: `theme/` (AKJ Events prototype colors), shared `component/`s, `util/RequestResult` (Loading/Success/Failure for future async operations).
- `navigation/` — the main NavHost, its type-safe routes, and `SessionViewModel` (role and unread alerts for the bottom bar). Tabs are opened with `openTab`, stacked on the role's root (Home for users, Moderation for moderators). Screens with a bottom bar receive it as a `bottomBar` slot. The map picker returns its result through the previous entry's `SavedStateHandle`.
- `domain/model/` — plain Kotlin models. `CommunityEvent` enforces invariants in `init` via `require` (at least one image, `endsAt` after `startsAt`, positive capacity, `REJECTED` requires `rejectionReason`). Constructing an invalid event throws.
- `domain/repository/` + `data/repository/remote/` (Firebase, used by the app) + `data/repository/InMemory*Repository` (used by unit tests) — repositories exposed as `StateFlow`s. Firestore DTOs live in `data/remote/` (all fields with defaults, `@Keep`; `FirestoreSupport.kt` has the `Timestamp` conversions and the `Query.listen` helper). They only store and query data; they never award points, send notifications or check permissions. Every one-shot read or write is `suspend` (only the observed lists are `StateFlow`), so the Firebase implementations replaced them without changing callers. Inside the in-memory implementations, `synchronized` sections use private non-suspend lookups (`eventById`, `userById`), because a suspend call is not allowed inside a critical section:
  - `UserRepository`: accounts, the session (`currentUser`, `login`, `logout`, `register`), profile edits, account deletion, and reputation data (`addPoints` returns a `PointsChange`, `addBadge` returns whether it was new). `User.level` is derived from points (`UserLevel.forPoints`).
  - `EventRepository`: events, comments, attendances (with `checkedIn`) and interests; `updateStatus`, `registerCheckIn`, `registerVerificationReward`. Capacity checks stay here because they must be atomic.
  - `NotificationRepository`: in-app notifications, read/unread.
  - `RecommendationRepository` (`LocalRecommendationRepository` + `LocalRecommendationRanker`).
- `domain/usecase/<area>/` — one class per action with `@Inject constructor` and `suspend operator fun invoke` (guide 12 of the course); `Observe*UseCase`s are not suspend and return the repository's `StateFlow`. They hold the community rules: permissions (only the organizer edits; organizer or moderator deletes/finishes; only moderators verify/reject, and rejecting needs a reason), points (`ReputationPoints`, via `AwardPointsUseCase`, which skips moderators and notifies level-ups), badges (`AwardBadgeUseCase`), and notifications (e.g. `AddCommentUseCase` notifies the event author). New and edited events are always saved `PENDING` by `CreateEventUseCase`/`UpdateEventUseCase`.
- `di/RepositoryModule` — Hilt `@Binds` from each repository interface to its `@Singleton` implementation: `FirebaseUserRepository`, `FirestoreEventRepository`, `FirestoreNotificationRepository` and `DataStoreSessionPreferences`; recommendations stay local. `di/CoroutinesModule` provides the `@ApplicationScope` used by repositories that listen to Firebase. `AKJEventsApp` is the `@HiltAndroidApp`, `MainActivity` is `@AndroidEntryPoint`. In-memory repositories keep an `@Inject constructor()` with the sample data and a primary constructor for tests.

ViewModels are `@HiltViewModel` and depend only on use cases (never on repositories). Screens get them with `hiltViewModel()` (from `androidx.hilt.lifecycle.viewmodel.compose`). ViewModels that need route arguments (`EventDetail`, `EditEvent`, `CheckIn`, `PickLocation`) read them from `SavedStateHandle` in their `@Inject` secondary constructor; their primary constructor takes the values directly so tests can call it. The same pattern provides test-only parameters (`now`, `simulatedRequestMs`). Tests build fresh, connected repositories with `TestRepositories` and their use cases with `TestUseCases` (both in `app/src/test`); the session opens as the demo user. Sample data lives in `data/demo/` (`SampleEvents`, `SampleUsers`, `SampleParticipation`, `SamplePlaces`); `seed/sample-data.mjs` is the same data for Firestore, so keep both in sync.
- `features/<feature>/` — screens and their ViewModels (e.g. `home/HomeScreen` + `HomeViewModel`, `event/detail/EventDetailScreen`).

Navigation uses type-safe Navigation Compose: routes are `@Serializable` members of the `sealed interface MainRoutes` (`navigation/MainRoutes.kt`) and are read back with `entry.toRoute<...>()` in `AppNavigation.kt`. To add a screen, add a route there and a `composable<Route>` entry in the NavHost. Screens receive navigation callbacks (`onOpenEvent`, `onBack`) instead of the `NavController`.

State pattern: a ViewModel exposes a `StateFlow<XUiState>` backed by a private `MutableStateFlow`, updated with `_uiState.update { it.copy(...) }`. Screens get it with `hiltViewModel()` and `collectAsState()`. ViewModels that observe data collect the flows returned by `Observe*UseCase`s in `viewModelScope`; lookups that need a suspend call (organizers, comment authors) are resolved inside the `combine` transform, not inside `_uiState.update`. User actions call use cases inside `viewModelScope.launch` wrapped in `runCatching` (guide 19): forms publish `RequestResult.Loading` first and turn failures into `RequestResult.Failure`; screens with a snackbar use a private `runAction` helper that ignores double taps and shows an error message. Unit tests need `MainDispatcherRule` (in `app/src/test`, an `UnconfinedTestDispatcher`, so launched work finishes immediately) and should create the ViewModel lazily, after the rule has set `Dispatchers.Main`; tests that call suspend functions use `runTest`.

Images load from URLs with Coil 3 (`AsyncImage`, see `core/component/EventImage`), using `res/drawable/event_placeholder.xml` as the fallback. Maps are drawn by `core/component/SimulatedMap` (real lat/lng, pan/zoom, markers, center-pin picking); QR codes are real (ZXing) but scanning is simulated by typing or picking the code.

## Domain rule: public visibility

Only `EventStatus.VERIFIED` events may appear publicly. `EventRepository.publicEvents`/`findPublicEvent` only return verified events and attendance, interest and check-in only work on them, so the feed and the map never show hidden events; `SampleEvents.findPublicById` applies the same rule. In the detail, `FINISHED` events are visible but closed, and `PENDING`/`REJECTED` ones are visible only to their organizer and to moderators; `firestore.rules` enforces the same rule, and in the app `events` only holds what the session may read (all events for moderators). New and edited events start as `PENDING`. The sample data includes pending, rejected and finished events (e.g. `pendiente-privado`, `rechazado-privado`, `reforestacion-rio`) and several owned by the demo user (`user-1`). `PublicEventVisibilityTest` and other tests assert counts from the sample data (8 verified events), so update them if you change it.

## Roadmap (from README)

The next stages are: backend for auth, data, and images; registration and login with `USER` and `MODERATOR` roles (moderators preloaded, permissions enforced in the DB); event CRUD with a map location; attendance, interests, comments, and notifications; stats, points, levels, and badges; server-verified QR check-in; and an AI category suggestion that always allows a manual override.
